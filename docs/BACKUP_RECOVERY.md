# Backup & recovery

LifeTrack is cloud-first: the hosted database is the master copy. There are three layers of protection — the **provider's database backups**, the **user's own exports** (web only) and **git** for code and built-in data.

## 1. What needs backing up

| Asset | Where it lives | Protected by |
| --- | --- | --- |
| User data (30 tables) | Supabase Postgres | Supabase backups / PITR (configure; not in the repo) + user JSON export |
| Accounts and password hashes | Supabase Auth schema | Supabase backups |
| Profiles and push tokens | `profiles`, `device_push_tokens` | Supabase backups only (**not** in the JSON export; tokens re-register by themselves) |
| Built-in foods, exercises, defaults | Git (`packages/constants`, `apps/web/public/exercises`) | Git; exercise photos are hash-verified and restorable with `exercises:sync` |
| Migrations | `supabase/migrations`, `supabase/setup-all.sql` | Git |
| Edge Function code and the cron SQL | `supabase/functions`; cron SQL is **manual** and kept only in `docs/NATIVE.md` | Git; re-run the SQL when rebuilding a project |
| Secrets (`CRON_SECRET`, signing keys, Firebase file) | Supabase secrets, EAS, a local keystore | **Not backed up by the repo.** Losing the Android signing key means users cannot update the app (`scripts/release-android.sh` header) |

## 2. User export (web → Data Export, `/export`)

**JSON backup** (`BackupCard`, `services/backup.js`)

- Reads every table straight from the database (not the cache) so the file is complete: `{app:'lifetrack', version:1, exported_at, tables:{…30 tables…}}`.
- Contains all rows of: the 29 `TABLES` plus `user_settings`. Does **not** contain `profiles`, `device_push_tokens` or built-in data.
- The file is plain, unencrypted JSON — store it somewhere private.

**CSV export** (`CsvCard`, `services/csv.js`): per table, 28 tables (see `EXPORTABLE`): the amount column is named after your currency; cells starting with `= + - @` are neutralised; a UTF-8 BOM is added for Excel; owner id omitted.
Reports can also be downloaded as CSV (Reports page).

**Mobile:** no export or restore UI (❌). Mobile-only users must use the web app with the same account.

## 3. Restore (web → Data Export → restore)

Restore is a **merge**, never a replace:

1. The file is parsed and validated (`parseBackup`): ≤ 50 MB, `app` must be `lifetrack`, `version` ≤ 1, ≤ 200,000 rows per table, known table names only, every row has an `id`.
2. Tables are processed parents-before-children (`TABLES` order), `user_settings` last; rows are upserted by `id` in chunks of 200 and **ownership is re-stamped** to the signed-in account.
3. For tables with a natural unique key (`learning_topics`, `exercises`, `health_logs`, `journal_entries`, `body_measurements`, `budgets`, `foods` (by `base_key`), `nutrition_settings`) rows that collide with existing ones are merged into the existing row
   (backup values win) and foreign keys that pointed at the backup's id are remapped (`goals.topic_id`, `study_sessions.topic_id`, `exercise_logs.exercise_id`, `food_logs.food_id`).
4. Duplicate "created as" `application_history` rows generated by the trigger are removed when the backup carries its own history.
5. On failure the error names the table and says nothing was deleted; **importing the same file again continues**.

Consequences: restoring into a non-empty account never deletes anything, running it twice is harmless, and items you deleted since the backup **come back**. To get an exact copy of a backup, erase first (§4) and then restore.

Fixed in the Unreleased changelog: restoring when nutrition targets or a starter-food copy already exist no longer fails with "That record already exists".

## 4. Erase all data

`EraseCard` (typed confirmation `ERASE`) deletes every record of the 29 data tables (children before parents) and keeps the account and `user_settings`. It applies to every signed-in device. It cannot be undone — download a JSON backup first.

## 5. Delete the account

Settings → Account → Delete (web and mobile) calls RPC `delete_my_account`, which deletes the user from `auth.users`; every row cascades. Then the session is signed out. There is no grace period or recovery.

## 6. Provider-level backup and recovery (recommended runbook)

1. Enable backups/PITR for the production project (Dashboard → Database → Backups). Take a manual backup before every migration run ([DEPLOY.md](DEPLOY.md)).
2. **Recover a table or the project:** restore from the dashboard (PITR/backup) into a new project, run any migrations newer than the backup, then point `VITE_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_URL` at it (a rebuild is needed because the values are inlined).
3. **Rebuild from scratch:** create a project, run `supabase/setup-all.sql`, re-apply Auth settings ([RELEASE.md](RELEASE.md) §2), redeploy the Edge Function with a new `CRON_SECRET`, recreate the cron job ([NATIVE.md](NATIVE.md)), then restore data from users' JSON exports.
4. Roll back a bad migration only with a new forward migration; code rollbacks redeploy the previous build.
5. Practice the restore once; no restore drill has been performed in this repository's history.

## 7. Gaps

- No automatic scheduled export, no mobile export, no encrypted export, no per-module partial restore, no "replace" restore mode.
- Backup version is `1` with no migration path defined for future schema changes (`version` > 1 is rejected).
- The JSON backup omits `profiles` (display name is re-created from auth metadata on sign-up).
- Cron SQL and secrets are not recoverable from the repository alone.
